# v2.4.1 Release + Peer Distribution Pattern

Use this when cutting a blocker-remediation release of `capability-reuse` and distributing it through peer70.

## Durable pattern

1. Treat reviewer blockers as executable regression specs first:
   - add hard-negative tests before implementation;
   - include direct-dispatch edge cases, not only retriever paths;
   - include release-validator failure cases such as archive SHA mismatch.
2. Keep release scope narrow for blocker-remediation versions:
   - provenance/hash reconciliation;
   - safety hard negatives;
   - unsupported target handling;
   - conformance wording/evidence-scope corrections;
   - validator hardening.
3. Before packaging, refresh runtime plugin and evidence:
   - sync `plugin/` to `~/.hermes/plugins/capability-reuse/`;
   - run `python3 -m compileall plugin tests scripts`;
   - run `python3 -m unittest discover -s tests -p 'test*.py'`;
   - run `python3 scripts/conformance-suite.py --profile full-required`;
   - copy/save the generated conformance report into versioned `evidence/`;
   - regenerate `evidence/deployment-manifest.json` and `evidence/SHA256SUMS` after the final source changes.
4. Package with a canonical sidecar and require validator agreement:
   - create `/tmp/capability-reuse-vX.Y.Z.zip` from the parent `skills/hermes` directory so the archive contains a single top-level `capability-reuse/` tree;
   - exclude `__pycache__`, `*.pyc`, and VCS files;
   - write `/tmp/capability-reuse-vX.Y.Z.zip.sha256`;
   - run `scripts/validate-release-archive.py ARCHIVE --version X.Y.Z --sha256-file SIDECAR`.
5. Send archive + sidecar + any registry data bundle to peer70, then let peer70 distribute to active reachable peers.
6. Peer distribution should verify on each target:
   - archive SHA matches sidecar;
   - archive validator passes locally on the peer;
   - skill tree and runtime plugin tree are installed;
   - registry/contracts are migrated when dispatcher semantics depend on registry data;
   - compileall passes.
7. After peer70 reports completion, run new-feature tests on every active reachable peer:
   - version surface equals the release version;
   - composite read+mutation prompts produce no active intervention;
   - unsupported peer targets are rejected before intervention;
   - direct `unsupported_target` dispatch is a clean fallback if that is part of the release;
   - conformance output keeps local-controller scope explicit;
   - supported `hmp-healthcheck` still succeeds against a known live peer such as peer70.
8. Report offline peers separately from failed peers. `No route to host` / unreachable peers are not distribution failures for active reachable peer rollout, but they remain pending for the next cycle.

## Pitfalls

- A `.sha256` sidecar created with an absolute archive path may fail `sha256sum -c` after copying to peer70; compare the hash value directly or rewrite the sidecar filename for the remote directory.
- `python3 -m unittest tests.test_...` may fail on peers where `tests/` is not import-package shaped; use discovery (`python3 -m unittest discover -s tests -p 'test_name.py' -v`) for portable peer checks.
- Do not rely only on local source registry changes. If `invoke_capability` clean-failure behavior depends on registry contracts, distribute a registry/contracts bundle or make the protocol robust to older registry data.
- Do not summarize local conformance as pinned Hermes CLI/gateway/delegated-agent proof unless those surfaces were actually exercised and raw evidence was captured.
