# v2.4.16 successor-source — version authority & T1-T6 validation battery (2026-08-13)

## Core lesson: deployment-manifest.json is the VERSION AUTHORITY

A peer can show `SKILL.md version: 2.4.16`, `plugin.yaml version: 2.4.16`,
and `protocol.py VERSION = "2.4.16"` while the **`evidence/deployment-manifest.json`**
still declares `artifact: capability-reuse-v2.4.7.zip`, `status:
v2.4.7_release_candidate_validated_source; live metadata cohort deployment
pending`. The manifest — not the version strings — is the authority for what
is actually deployed.

**Rules agreed with peer106 (2026-08-13):**
- A newer local version (2.4.16) is a **successor source / WIP**, NOT a
  promoted release, even when all internal version surfaces agree.
- Promotion to 2.4.16 happens ONLY after, in order:
  1. Rebuild/review of the 2.4.16 archive (canonical ZIP + SHA-256 sidecar)
  2. All internal version surfaces aligned inside the archive (SKILL.md,
     plugin.yaml, protocol.py, event_schema_version, review_schema_version)
  3. `deployment-manifest.json` updated to 2.4.16 with matching artifact hash
  4. Clean deployment boundary (fresh cohort after restart)
  5. Live metadata/cohort proof from a real organic hook event
- Until then: manifest status stays "2.4.7 selected/pending", 2.4.16 is
  "successor source pending artifact+manifest promotion".
- Do NOT patch a release in place while still identifying it as the
  unchanged original (same rule as the zip-filename trap, but at manifest
  level).

## Detecting the discrepancy (T1)

```bash
# Version surfaces on the peer:
grep '^version' ~/.hermes/skills/hermes/capability-reuse/SKILL.md
grep -r 'version' ~/.hermes/skills/hermes/capability-reuse/plugin/plugin.yaml | head -2
grep -n 'VERSION' ~/.hermes/skills/hermes/capability-reuse/plugin/protocol.py | head -3
# The authority:
python3 -m json.tool ~/.hermes/skills/hermes/capability-reuse/evidence/deployment-manifest.json
# Runtime tree hash (exclude pycache/transient):
find . -type f \( -name '*.py' -o -name '*.md' -o -name '*.yaml' -o -name '*.json' -o -name '*.sh' \) \
  -not -path '*__pycache__*' -not -path '*/.git/*' | sort | xargs sha256sum | sha256sum
```

If manifest version ≠ SKILL.md/plugin/protocol version → the local tree is
ahead of the deployed release: do not treat it as live evidence, ask the
peer where it came from before promoting.

## T1-T6 validation battery (agreed with peer106, 2026-08-13)

Order: T1 → deploy/restart clean cohort → T2 → T3/T4 → T5 → T6.

- **T1 Artifact Identity** — live gateway PID + start time after restart;
  loaded plugin path; plugin/protocol/event-schema versions; runtime tree
  hash excluding `__pycache__`/`.pyc`/transient; compare against manifest/
  sidecar (not filename); deployment_id + timestamp. Archive SHA ≠ tree SHA
  in form — compare via manifest/file hashes or expected tree hash from a
  clean extraction.
- **T2 Clean Cohort** — one REAL organic hook event (`pre_llm_call`/
  `pre_tool_call` on the live gateway), not a script, direct emit, CLI, or
  acceptance fixture. Required metadata: deployment_id, deployment_timestamp,
  plugin_version, artifact_hash, event_schema_version, requester_peer,
  processing_peer, target_peer, authoritative retrieval_event_id, validated
  inputs, clean cohort membership. **PASS fails if fresh organic events = 0.**
- **T3 Disposition Accounting** — every retrieval event gets exactly one
  disposition (review row / excluded w/ reason / duplicate / malformed /
  outside cohort / unsupported schema / no reviewable candidate / orphan).
  Chain errors reported separately (retrieval w/o start, start w/o
  completion, completion w/o start, duplicate completion, identifier
  mismatch). Gate: zero unexplained orphans (retrieval AND chain).
- **T4 Eligibility Fail-Closed** — `formal_holdout_eligible` is COMPUTED
  from trusted fields, never accepted as an input flag. Rejection reasons:
  legacy_schema, unsupported_schema, missing_artifact_hash,
  wrong_plugin_version, wrong_deployment_id, invalid_provenance,
  non_organic_traffic, unknown_requester, unknown_processing_peer,
  outside_cohort. Legacy/acceptance/synthetic/test traffic must compute false.
- **T5a Reversed/Rejection** — composite/mutating prompt ("check health and
  restart if unhealthy") must NOT open an active read-only decision, or be
  excluded/rejected with structured reason.
- **T5b Cross-Peer** — the PROCESSING peer must emit its own
  retrieval/intervention/invocation chain with live metadata. A remote
  HMP health response alone is NOT evidence. Verify on the peer: PID/start
  time changed after restart, plugin loaded, `CAPABILITY_REUSE_*` env,
  fresh post-restart retrieval event. (Remote deploy pitfall: copying files
  does not prove the running gateway loaded them — check PID/lstart.)
- **T6 Scope / Non-Generalization** — report must declare: validation
  limited to peer106+peer58; no generalization to the wider fleet;
  thresholds valid only for this deployment/registry/capability set/traffic
  mix.
