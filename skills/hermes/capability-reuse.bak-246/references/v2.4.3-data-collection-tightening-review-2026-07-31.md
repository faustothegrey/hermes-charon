# v2.4.3 data collection tightening review — 2026-07-31

External review of the first live harvesting report found the collector is working, but the data is not yet acceptable for Phase 0 metrics. Treat this as executable acceptance criteria before claiming current precision, recurrence, calibration, or Phase 0 closure.

## Highest-priority blockers

1. **Request-scoped mandatory provenance**
   - Every new retrieval event must carry:
     ```json
     {
       "plugin_version": "2.4.3",
       "schema_version": "1.1",
       "provenance": {
         "stream": "organic_live",
         "source": "gateway",
         "detail": "normal_user_request"
       }
     }
     ```
   - Do not infer missing/invalid provenance as organic.
   - Missing metadata → `legacy_unclassified`.
   - Invalid value → `unknown`.
   - Valid explicit value → accepted stream.
   - Provenance must come from the request or hook context, not a process-wide environment variable.

2. **Record `peer_id` on every event**
   - Required on retrieval, execution-start, execution-completion, and review records.
   - Blank peer IDs make cross-peer recurrence, cron/test traffic, fleet regressions, and peer-local false matches indistinguishable.

3. **Separate clean v2.4.3 live data from backlog**
   - Define an immutable cohort boundary with:
     - `deployment_id`
     - `deployment_timestamp`
     - `plugin_version`
     - `plugin_artifact_hash`
     - `schema_version`
   - Publish separate reports:
     - `legacy_or_pre_2.4.3`
     - `v2.4.3_clean_live`
   - Only `v2.4.3_clean_live` counts toward current precision, recurrence, or calibration.

4. **Complete event-chain correlation**
   - Each retrieval/start/completion chain must share:
     - `session_id`
     - `episode_id`
     - `turn_id`
     - `task_id`
     - `tool_call_id`
     - `retrieval_event_id`
     - `code_hash`
   - Analyzer must report:
     - retrieval without execution
     - start without completion
     - completion without start
     - duplicate completion
     - identifier mismatch
   - Formal criterion: zero unexplained chain errors, not merely equal aggregate start/completion counts.

5. **Distinguish traffic types and deduplicate recurrence**
   - Add fields:
     - `traffic_type`: `organic_user`, `cron`, `test`, `retry`, `calibration`, `unknown`
     - `parent_task_id`
     - `retry_of`
     - `schedule_id`
   - Recurrence metrics must report both raw occurrences and independent occurrences.
   - Retries in one session must not count like independent tasks across sessions/peers.

6. **Improve row-level review data and preserve labels**
   - Review export should include:
     - `event_id`
     - redacted request
     - top candidate and version
     - top score
     - second candidate and score
     - score margin
     - eligibility result
     - filter rejection reasons
     - request effect
     - capability effect
     - whole-request coverage
     - provenance
     - peer_id
     - session_id
     - traffic_type
     - human label
     - reviewer
     - review timestamp
   - Preserve human labels in a separate append-only file or database. Regenerating the review queue must never erase completed labels.

## Also fix

- Time-window reports must use event timestamp, not analyzer run time.
- Keep read-only and mutating candidates in separate review and metric streams.
- Apply CSV formula neutralization before exporting user-controlled text.

## Minimum acceptance test for next collection run

After deploying fixes, collect 20–30 fresh retrieval events and require:

- 100% `plugin_version` present
- 100% artifact hash present
- 100% valid provenance
- 100% `peer_id` present
- 100% `traffic_type` present
- 100% correlated event chains
- 0 legacy events in clean cohort
- 0 human labels lost after refresh
- 0 mutating candidates mixed into read-only metrics

## Current decision

Collection volume is already sufficient for first review, but not for Phase 0 metrics. Remaining work: make every record attributable, separable, and reproducible.
