## Why formal empirical closure failed

### C4 — Pre-execution labels failed

The package contained 120 request-to-capability pairs, but:

- 72/120 were synthetic;
- the full 60-example holdout was synthetic;
- holdout prompts used repeated templates with suffixes like `variant 1`, `variant 6`;
- the same ten base templates appeared on both sides of tuning/holdout;
- labels were generated automatically rather than manually or independently reviewed.

This violates the approved criterion:

```text
C4: ≥100 pairs — Manual labeling
```

The v1.6 design requires tuning and holdout pairs using actual hook-visible input, including meaningful hard negatives.

### C5 — Post-execution labels failed

The 150 post-execution pairs were generated by deterministic operation equality:

```python
same = a["operation"] == b["operation"]
label = "same_operation" if same else "unrelated"
```

The operation category itself was assigned by regex, so the supposed ground-truth label was circular.

Dataset composition problem:

```text
129 same_operation
21 unrelated
0 related-but-different
0 incompatible
0 uncertain
```

It used only 30 unique messages and was dominated by `json_aggregation`.

The expected benchmark must cover same, materially different, unrelated, incompatible, and uncertain cases.

### C6 — Precision measurement invalid

The reported 100% precision/recall was circular because labels and predictions were both produced by similar regex logic.

In plain terms: it measured whether one keyword classifier agreed with another keyword classifier, not whether the actual retriever correctly chose capabilities.

Formal C6 requires evaluating the actual retriever pipeline:

- real candidate scores;
- top-1/top-2 margin;
- hard filters;
- eligibility;
- registry contracts;
- final intervention decision.

### C7 — Effect-class safety not independently demonstrated

Zero read-only↔mutating false matches came from the same generated hard-negative rules used by the predictor. This only proves the guard handles its own templates, not that the retriever avoids real mutating/read-only mismatches.

### C8 — Runtime conformance unproven

The 15/15 reports are useful local integration harness evidence, but they are still partly simulated. Reviewer wants raw proof that hooks fire through real pinned runtime surfaces:

- real Hermes CLI turn;
- real gateway request;
- real dispatcher path;
- real co-resident plugin block or explicitly marked unsupported;
- real approval pipeline;
- delegation either genuinely tested or explicitly unsupported/unknown, not simulated as pass.

### C10 — Threshold selected, not calibrated

The report claimed active threshold 0.65, but:

- code default remains 0.75;
- no threshold sweep was included;
- no precision/recall curve was included;
- no tuning results by threshold were included;
- no top-vs-second margin calibration was included;
- no lower confidence bound was calculated;
- the holdout was synthetic/leaky and cannot be used for calibration.

The 0.65 value was an engineering choice based on observed smoke prompts, not benchmark calibration.

## Other methodological concerns

### C2 recurrence clusters

Reported clusters were regex operation buckets:

```text
json_aggregation
file_patch

hmp_send

```

They were not independently discovered/validated syntax-capability-effect fingerprint clusters. `test_validation` may be implementation/debugging activity rather than recurring user demand. Need manual validation across sessions/days and exclusion of retries/debug loops.

### C3 coverage calculation

Reported 100% coverage was misleading because there were only eight operation buckets, so top-10 included everything including `unknown_other`. Corrected recognized recurring coverage is likely:

```text
252 / 301 = 83.7%
```

This likely still passes ≥40%, but the calculation and report must be corrected.
