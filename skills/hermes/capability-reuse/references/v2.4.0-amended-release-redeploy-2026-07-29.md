# Capability-reuse v2.4.0 amended release and redeploy runbook — 2026-07-29

## When to use

Use this when a capability-reuse release is rejected because the packaged plugin entrypoint bypasses the controller, or when promoting an amended capability-reuse package after review finds release-assembly drift.

## Durable lesson

If a review rejects a numbered archive, do not redeploy an ambiguous `vX.Y.Z-corrected` artifact as the canonical release. Promote the amended package to the next clean version number, align all visible version surfaces, regenerate evidence and checksums, then redeploy that version.

For this session, the rejected artifact was v2.3.0. The corrected release is v2.4.0.

## Version surfaces that must agree

Before packaging, align at least:

- `SKILL.md` frontmatter `version`
- `plugin/plugin.yaml` `version`
- `plugin/protocol.py::VERSION`
- `evidence/deployment-manifest.json` `version`, `skill_version`, `plugin_version`, `protocol_VERSION`, and `artifact`

If these represent distinct schema/component versions in a future release, document that explicitly in the manifest. Otherwise, mismatched versions are a release blocker.

## Entrypoint regression checklist

For capability-reuse, top-level `plugin/__init__.py` must route through the protocol controller, not call lower-level modules directly:

- `on_pre_llm_call()` calls `ctrl.retrieve(...)`
- active decisions are persisted with `ctrl.persist_intervention(...)`
- prompt injection is rendered by `ctrl.render_injection(...)`
- `on_pre_tool_call("execute_code", ...)` calls `ctrl.authorize_execute_code(...)`
- blocked execute-code calls return `{"action": "block", "message": ...}`
- non-execute-code arbitrary execution surfaces go through `ctrl.observe_alternate_tool_if_relevant(...)`
- `on_post_tool_call()` calls `ctrl.record_tool_outcome(...)`
- runtime mode is read dynamically via `_mode()`, not captured once at import time

Regression coverage should prove:

- shadow mode hides `invoke_capability`
- active mode exposes `invoke_capability` after env changes in the same process
- active retrieval injects a healthcheck intervention
- active raw `execute_code` blocks while the intervention is open
- execute-code started/completed events preserve `session_id`, `episode_id`, `turn_id`, `tool_call_id`, and `retrieval_event_id`
- blocked completions log `outcome=blocked` and `block_origin=protocol`

## Peer redeploy pattern

On each peer:

```bash
cd ~/.hermes/skills/hermes
rm -rf capability-reuse
unzip /tmp/capability-reuse-v2.4.0.zip -d ~/.hermes/skills/hermes

rm -rf ~/.hermes/plugins/capability-reuse
mkdir -p ~/.hermes/plugins/capability-reuse
cp -a ~/.hermes/skills/hermes/capability-reuse/plugin/. ~/.hermes/plugins/capability-reuse/
```

Preserve `hmp` in `plugins.enabled`; add `capability-reuse` if absent. Then restart/reload the Hermes gateway/agent for that peer.

Post-deploy validation on each peer:

```bash
cd ~/.hermes/skills/hermes/capability-reuse
python3 -m compileall plugin tests scripts
python3 -m unittest discover -s tests -p 'test*.py'
python3 scripts/conformance-suite.py --profile full-required

test ! -d capability-reuse && echo "no nested duplicate"
```
