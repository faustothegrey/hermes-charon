# v2.4.16 clean-cohort live metadata gates (2026-08-02)

Reusable lesson from the peer58/peer106 Phase 0 remediation run. This is a gate-ordered procedure for selecting a fixed release, deploying it with a clean cohort, and proving that live organic hook events carry enough metadata for formal review.

## Gate order

Follow the reviewer's gate order exactly; do not start positive reuse cases until the live metadata path passes.

1. Identify the exact artifact currently running:
   - live process PID and start/restart timestamp;
   - loaded plugin path;
   - plugin/protocol/event-schema versions;
   - runtime plugin-tree hash;
   - deployment ID and timestamp.
2. Select the exact fixed release archive; do not rely on the filename or version string alone.
3. Verify archive SHA-256 against an external sidecar/manifest and verify aligned version surfaces inside the archive.
4. Deploy that reviewed artifact and start a new clean cohort.
5. Prove one genuine organic hook event carries complete deployment metadata before running reuse cases.
6. Account for every retrieval/execution-chain event with exactly one structured disposition.
7. Only then run positive, reversed positive, and composite-rejection cases.

## Artifact identity checklist

For each candidate release, capture:

- source archive path;
- external SHA-256 sidecar or manifest;
- archive SHA-256;
- release manifest;
- test report;
- scoped conformance report;
- internal version surfaces (`SKILL.md`, `plugin/plugin.yaml`, `plugin/protocol.py`, metadata helpers);
- deployed runtime tree hash after extraction.

Do not patch a release in place while still identifying it as the unchanged original release. If live-path fixes are in a later release, select and review the later release.

## Clean cohort event metadata

Every event in the current-release cohort must include trusted metadata, not analyzer-inferred defaults:

- `deployment_id`;
- `deployment_timestamp`;
- `plugin_version`;
- `plugin_artifact_hash` or runtime tree hash;
- `event_schema_version`;
- valid request-scoped organic provenance;
- `traffic_type`;
- requester, processing peer, and target peer when applicable.

Everything before the deployment boundary is legacy/outside-cohort and must be excluded from current-release metrics.

## Organic-hook proof pattern

Use a trivial real hook-path request, not direct `emit_retrieval()` or an acceptance fixture. Inspect the resulting retrieval event and require all fields to be nonblank and correct:

- authoritative retrieval event ID;
- requester peer;
- processing peer;
- target peer when applicable;
- request-scoped provenance (`organic_live`, valid true);
- traffic type (`organic_peer` or another allowed organic type);
- validated inputs;
- plugin version;
- artifact hash;
- deployment ID.

A response from the remote peer is not enough: the processing peer must emit a matching retrieval/intervention/invocation chain from its own live hook path.

## Remote deploy/restart pitfall

Copying reviewed plugin files to a peer does not prove the running gateway loaded them. After remote deployment, verify all of:

- file archive hash and installed runtime tree hash;
- gateway PID and `lstart` changed after the intended restart;
- plugin version surfaces visible in the loaded runtime;
- capability-reuse hooks are registered/loaded in the live gateway;
- a fresh post-restart organic request creates a retrieval event on that peer.

If the gateway PID/start time does not change and no fresh retrieval event appears, mark reversed or cross-peer cases blocked rather than treating the remote response as evidence.

## Disposition accounting

Analyzer/review generation must assign every retrieval event exactly one disposition:

- review row produced;
- excluded with a structured reason;
- duplicate;
- malformed;
- outside cohort;
- unsupported schema;
- no reviewable candidate;
- unexplained orphan.

Also report chain correlation errors separately:

- retrieval without execution start;
- start without completion;
- completion without start;
- duplicate completion;
- identifier mismatch.

Gate passes only with zero unexplained retrieval or execution-chain orphans. Explicit exclusions are acceptable when the reason is structured and reviewable.

## Formal eligibility computation

`formal_holdout_eligible` must be derived from trusted event fields and fail closed. Do not accept it as an input flag. Required trusted fields include:

- expected schema version;
- expected plugin version;
- deployment ID;
- artifact hash;
- valid organic provenance;
- allowed organic traffic type;
- known requester;
- known processing peer;
- clean cohort membership.

Emit explicit rejection reasons such as `legacy_schema`, `missing_artifact_hash`, or `non_organic_traffic`. Legacy, acceptance, synthetic, and test traffic must compute false.

## Scope statement

Evidence bundles for the current peer58/peer106 validation must include this scope statement or equivalent wording:

> Validation is currently limited to peer58 and peer106. Cross-peer observations refer only to recurrence between these two peers and must not be generalized to the wider fleet. Threshold observations remain specific to this deployment, registry, capability set, and traffic mix.
