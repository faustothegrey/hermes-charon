# v2.4.18 — Telemetry/Correlation Correctness Release (spec from external reviewer)

**Source:** external agent analysis of the v2.4.16 event archive (sent via email
per `email-packaging.md`), 2026-08-14. Adopted by Fausto as the third change of
the 2.4.18 release. This is an **executable specification**, not narrative
feedback — implement each point, then run the release gate.

## Release intent

v2.4.18 is a **telemetry/correlation correctness release**, NOT a
capability-expansion release. Objective: make one real request traceable
ingress → retrieval → decision → execution/non-execution → review, with
unambiguous producer identity and correct semantics.
**No** new capabilities, no threshold tuning, no hmp-send activation, no
multi-peer batch, no fleet rollout, no recurrence/precision claims, no attempt
to rehabilitate v2.4.6 evidence.

## Cohort policy

- v2.4.6  → legacy, excluded
- v2.4.16 → previous diagnostic cohort
- v2.4.18 → current evaluation cohort (new cohort is MANDATORY)

Every v2.4.18 event carries: `plugin_version=2.4.18`, unique `deployment_id`,
`deployment_timestamp`, real immutable `plugin_artifact_hash`,
`cohort_label=v2.4.18_live`, `event_schema_version=1.3`.
Acceptance: zero v2.4.18 events with a v2.4.5/v2.4.6 cohort or placeholder
artifact hash. Prefer **filtering** old cohorts out of analysis
(`--plugin-version`, `--deployment-id`) over deleting the original data.

## The 15 spec points

1. **New v2.4.18 cohort** — schema bump 1.2 → 1.3 (semantics change, not cosmetic).
2. **Explicit event producer** — every event:
   `{"producer": {"component": "capability_reuse_plugin", "version": "2.4.18", "surface": <surface>}}`.
   Surfaces: `hermes_cli`, `gateway`, `hmp_ingress`, `execute_code_hook`,
   `delegated_agent`. An HMP message observer and the actual plugin are not
   necessarily the same execution surface.
3. **Stop fake execute_code_* for generic HMP processing** — v2.4.16 emitted
   `execute_code_started/completed` for registry-sync/HMP messages with no
   evidence execute_code ran. Reserve those event types for real execute_code;
   use `surface_execution_started_event` / `surface_execution_completed_event`
   with `execution_surface=hmp_plugin` instead. Acceptance: a request handled
   without execute_code generates zero execute_code_* events.
4. **One correlation envelope through the whole chain** — immutable envelope:
   `trace_id, session_id, episode_id, turn_id, task_id, tool_call_id,
   retrieval_event_id, requester_peer_id, processing_peer_id, traffic_type,
   provenance` (+ optional target/collector). Add a top-level `trace_id` for
   trivial joins. Never reconstruct IDs from timestamps. Acceptance:
   `retrieval.trace_id == decision.trace_id == invocation.trace_id ==
   completion.trace_id == review.trace_id` for 100% of test cases.
5. **Explicit retrieval semantics** — v2.4.16 reported
   `candidate_count=0, top_score=0, whole_request_covered=true, eligibility=rejected`
   which is impossible. Introduce explicit stages:
   `retrieval.executed`, `coverage.evaluated` (`whole_request_covered=null` if
   not evaluated), `eligibility.evaluated` (`eligible=null` if not evaluated;
   `not_applicable` when no candidate). Never default booleans to values that
   imply a successful evaluation.
6. **Prove the retriever ran** — for every retrieval event:
   `retriever_version, registry_version/hash, threshold, minimum_margin,
   candidate_count, top/second candidate, top/second score, margin, filter
   results`. If only observing without running retrieval, emit
   `retriever_executed=false` (or a different event type) — never a fake
   zero-score retrieval_event.
7. **Composite-rejection semantics (key negative test)** — request
   `check peer58 health and restart it if unhealthy` must produce:
   candidate `hmp-healthcheck@1.0.0`, `validated_inputs.peer_list=["peer58"]`,
   `candidate_relationship=partial_match`, `whole_request_covered=false`,
   `request_effect=mutating`, `capability_effect=read_only`,
   `eligibility=rejected` with reason `partial_coverage` or `effect_mismatch`,
   `dispatch=none`. NOT `candidate_count=0`, NOT `whole_request_covered=true`.
8. **Traffic taxonomy** — explicit categories: `organic_user, organic_peer,
   scheduled_protocol, registry_sync, cron, retry, test, acceptance,
   calibration, unknown`. `registry sync?` → `registry_sync`; exclude
   registry_sync from recurrence/precision unless analyzing protocol traffic
   (29 repeated sync messages dominated the v2.4.16 dataset).
9. **Separate requester/processor/target permanently** — do not overload
   `processing_peer_id` with the telemetry collector; if peer70 only
   transports/collects, represent it as `collector_peer_id=peer70`.
10. **Only three functional cases initially** — Case A (peer106 → check HMP
    health for peer58; require full trace + review row), Case A reversed
    (peer58 → peer106; catches identity hardcoding), Case B (health +
    restart-if-unhealthy; candidate recognized then structured rejection).
    Only after these pass, resume passive bulk collection.
11. **Review record from the same trace** — `review.trace_id == request.trace_id`,
    `review.retrieval_event_id == retrieval.event_id`. Review data: redacted
    request, requester, processor, target, candidate+version, top/second
    score, margin, validated inputs, coverage, effects, eligibility decision,
    rejection reason, preview, actual outcome. Case A label: ACCEPT/exact_match;
    Case B: REJECT/partial_coverage.
12. **Label persistence part of acceptance** — label the two cases, regenerate
    the queue, confirm labels remain, supersede one label, confirm a new ledger
    record was appended and the previous record untouched. One canonical ledger.
13. **Reject stale analyzer reports automatically** — every report carries
    `input_event_log_sha256, input_event_count, input_min_timestamp,
    input_max_timestamp, analyzer_version, generated_at`. Consumers reject when
    hash ≠ current event-log hash or the covered range excludes the cohort.
14. **Cohort-specific analyzer filtering** — support
    `--plugin-version 2.4.18 --deployment-id dep-v2418-...` and report included
    events / excluded legacy / excluded producer versions / excluded traffic
    classes. Prevents contamination without deleting data.
15. **Formal holdout eligibility remains computed (derived only)** — require:
    `plugin_version==2.4.18`, correct deployment_id, correct artifact_hash,
    valid provenance, allowed organic traffic, known requester, known processor,
    schema==1.3, complete trace envelope. registry_sync/test/acceptance/
    calibration traffic automatically evaluate to false.

## Release gate (all must PASS)

1. exact v2.4.18 artifact identity on every event
2. one producer/surface identified on every event
3. no fake execute_code events
4. 100% correlation envelope propagation
5. Case A end-to-end
6. reversed Case A end-to-end
7. Case B candidate-recognized-and-rejected
8. two review labels persist after regeneration
9. acceptance produces zero production deltas
10. analyzer report tied to exact event-log hash

Any failure → keep v2.4.18 in diagnostic/passive mode.

## Implementation status (2026-08-14, peer70)

Implemented and unit-tested (schema 1.3 events written and read back):

- `event_store.py`: `SCHEMA_VERSION="1.3"`, `ENVELOPE_KEYS`,
  `DEFAULT_PRODUCER`, `VALID_SURFACES`; `emit()` now injects `producer`
  (component/version/surface — surface falls back to `data.producer_surface`)
  and top-level `trace_id` (from context or session_id); envelope keys are
  propagated from context into every event.
- New event types `surface_execution_started_event` /
  `surface_execution_completed_event` + `emit_surface_execution_start/complete`
  (fields: execution_surface, surface_preview, session, requester/processing
  peer, trace_id, traffic_type, producer_surface, outcome, duration_ms).
- `emit_retrieval()` extended with `trace_id, requester_peer_id,
  processing_peer_id, target_peer_id, collector_peer_id, producer_surface,
  retriever_executed` params (all optional, backward compatible).
- `plugins/hmp/adapter.py` consumer_loop: replaced `emit_execute_code_start/
  complete` with `emit_surface_execution_start/complete`
  (`execution_surface="hmp_plugin"`, `producer_surface="hmp_ingress"`,
  trace_id = chat_id, requester=from_peer, processing=self.node_id).

**Remaining (next sessions):** points 5-6 (explicit retrieval stages +
retriever proof in `retriever.py`), 7 (composite rejection semantics),
8 (traffic taxonomy), 10-12 (three cases + review from trace + label
persistence), 13-14 (analyzer hash + cohort filtering), 15 (holdout v2.4.18
conditions), then the 10-item release gate.

## Pitfalls learned on the way

- The plugin **runtime** (`~/.hermes/plugins/capability-reuse/`) and the skill
  source (`~/.hermes/skills/hermes/capability-reuse/plugin/`) are separate
  installs — a skill release is not deployed until BOTH agree on every peer
  (see `plugin-runtime-vs-skill-divergence-2026-08-14.md`). This also caused
  stale-version events to keep flowing into events.jsonl.
- Version-cleanup on events.jsonl: back up (`cp events.jsonl
  events.jsonl.bak-<ver>`), filter lines by `data.plugin_version`, then
  REGENERATE derived review files (`scripts/generate-review-queue-v245.py`)
  — old candidates/queues/CSVs still reference removed events otherwise.
- New plugins must be listed under `plugins.enabled` in config.yaml or
  discovery will not load them (46→47 enabled when harness-feedback was added).
- `*.bak-*` directories inside `skills/hermes/` collide as skill names — keep
  backups outside the skills tree.
