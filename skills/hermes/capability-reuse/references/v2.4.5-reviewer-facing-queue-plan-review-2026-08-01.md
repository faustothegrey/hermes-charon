# v2.4.5 reviewer-facing queue plan review — 2026-08-01

## Verdict

Approved with important changes before implementation.

Scope is intentionally narrow and approved: one reviewer-facing queue, one capability, one deterministic preview. The plan solves the human-labeling usability problem without expanding active reuse.

Core identity distinction to preserve everywhere:

- `requester_peer_id` = who originated the request
- `processing_peer_id` = which Hermes node processed it
- `target_peer_id` = which peer the capability would act upon

These must remain separate throughout events, analysis, exports, and labels.

## Required implementation changes

### 1. Do not export unredacted original text

Do not include both `original_text` and `redacted_text` in review artifacts. Human-review CSV, JSONL, Markdown, and dashboard outputs must contain only redacted request text.

Use:

```yaml
request:
  redacted_text: "check HMP health for peer128"
  raw_request_ref: "event:evt_..."
  redaction_status: "applied"
```

Raw request may remain only in the protected event store if operationally necessary. Privileged raw lookup must be separate and non-default.

### 2. Separate actor identity from transport

Do not merge actor identity and request channel.

Recommended internal shape:

```yaml
requester:
  actor_type: human | agent | scheduler | service | unknown
  actor_id: "telegram_user:sha256:..." | "hmp:peer106" | ...
  requester_peer_id: peer106
  request_channel: telegram | hmp | cron | local | api | gateway | unknown
```

A simplified reviewer-facing `requester_type` may still be exposed, but internally actor and transport remain orthogonal. Telegram IDs must be stable pseudonyms/hashes, not raw account IDs/usernames.

### 3. Generate preview from the same canonical execution plan as dispatch

Do not duplicate dispatcher logic in preview code. Use a shared exact-version-aware execution plan builder:

```python
plan = build_execution_plan(capability_id, capability_version, validated_inputs)
preview = redact_execution_plan(plan)
result = execute_execution_plan(plan)
```

The preview function must be pure, deterministic, network-free, secret-free, exact-version-aware, and must use the same allowlisted peer map as the dispatcher. It must not resolve targets from untrusted user-provided addresses.

For `hmp-healthcheck@1.0.0`, canonical plan shape:

```json
{
  "capability_id": "hmp-healthcheck",
  "capability_version": "1.0.0",
  "effect_class": "read_only",
  "target_peer_id": "peer128",
  "executor_kind": "http_get",
  "method": "GET",
  "endpoint": "http://192.168.178.128:18643/hmp/health",
  "timeout_seconds": 5,
  "auth_mode": "none",
  "mutation_possible": false
}
```

### 4. Replace `credentials_required` with clearer auth fields

Use:

```yaml
auth_mode: none | ambient | token | mTLS | unknown
credentials_exposed_in_preview: false
```

Acceptance must require `credentials_exposed_in_preview = false`.

### 5. Do not call a shadow candidate “selected”

In passive/shadow mode, Hermes has not selected or invoked anything. Use:

```yaml
retrieval:
  candidate_capability: hmp-healthcheck@1.0.0
  candidate_rank: 1
  candidate_score: 0.88
  eligibility_result: eligible_shadow_only
```

Reserve `selected_capability` for active intervention or explicit human acceptance.

### 6. Define label semantics precisely

Reviewer labels:

- `ACCEPT`: capability and preview fully cover the whole request, with compatible effects and correct target.
- `REJECT`: capability is unrelated, only partially covers the request, wrong target, or incompatible effects.
- `UNSURE`: available request/provenance data are insufficient for a reliable decision.

Structured reason codes:

- `exact_match`
- `partial_coverage`
- `wrong_capability`
- `wrong_target`
- `effect_mismatch`
- `informational_only`
- `code_generation_request`
- `composite_request`
- `requester_unclear`
- `preview_incorrect`
- `insufficient_context`
- `other`

Free-text notes may supplement, not replace, reason_code.

### 7. Use stable review IDs and a separate append-only label ledger

Generate deterministic review IDs from:

- `retrieval_event_id`
- candidate capability ID
- candidate version
- candidate rank

Example:

```python
review_id = sha256(retrieval_event_id + capability_id + capability_version + candidate_rank)
```

Separate generated candidates from human labels:

- `review/candidates-v245.jsonl`
- `review/human-labels.jsonl`
- `review/queue-v245-review.csv`
- `review/queue-v245-review.jsonl`

`human-labels.jsonl` must be append-only:

```yaml
review_id: ...
label: ACCEPT
reason_code: exact_match
notes: ...
reviewer: ...
reviewed_at: ...
supersedes_label_id: null
```

Displayed queues are joins between candidates and the latest label.

### 8. Add preview status and target-resolution evidence

Add:

```yaml
intended_execution:
  preview_status: exact | unresolved | unsupported | invalid_input
  target_resolution_source: peer_map | validated_input | unavailable
```

Unsupported targets must not receive executable previews. Example:

```json
{
  "preview_status": "unsupported",
  "target_peer_id": "peer999",
  "executor_kind": "unresolved",
  "command_preview": "NOT EXECUTABLE: unsupported target peer"
}
```

Such candidates should generally get `eligibility_result = ineligible_environment_constraint`.

### 9. Bump event schema and define review/preview schemas

Recommended versions:

- skill version: `2.4.5`
- retrieval event schema: `1.2`
- review record schema: `1.0`
- preview schema: `1.0`

Every exported row must include relevant schema versions.

Legacy records without requester metadata:

```yaml
requester_type: unknown
provenance: legacy_unclassified
formal_holdout_eligible: false
```

Do not infer requester identity retrospectively.

### 10. Split deterministic tests from live acceptance run

Two layers are required.

#### Deterministic integration tests

Fixtures must cover:

- HMP requester and different target peer
- Telegram requester
- cron requester
- unknown requester
- unsupported peer
- redaction
- formula injection
- queue refresh preserving labels
- no secret-bearing preview
- exact expected healthcheck plan

#### Live v2.4.5 smoke test

Collect 20–30 events and verify deployed runtime field completeness/routing.

Both layers must pass and produce separate reports.

Synthetic acceptance rows must be excluded from Fausto’s real labeling queue. Use separate outputs:

- `queue-v245-acceptance.csv`
- `queue-v245-organic-review.csv`

Organic review queue includes only valid streams:

- `organic_user`
- `organic_peer`

Exclude from organic review:

- `acceptance_test`
- `calibration_probe`
- `operator_seeded`
- `legacy_unclassified`
- `unknown`

These may still appear in operational dashboards.

## Acceptance criteria

Release can report `VERDICT: PASS` only when:

- All new retrieval events use schema `1.2`.
- All events contain a requester block.
- Unknown requester information remains explicitly unknown.
- Requester, processing peer, and target peer are independently tested.
- Every review row contains a deterministic execution preview or explicit unresolved status.
- Preview and dispatcher derive from the same execution-plan builder.
- No raw request or secret is exported.
- No unsupported target receives an executable preview.
- Human labels survive repeated analyzer runs.
- CSV formula injection is neutralized.
- Synthetic events are excluded from the organic review queue.
- Markdown sample is generated from the same review record, not separately constructed.
- Deterministic test suite passes.
- Deployed 20–30-event smoke test passes.

## Final assessment

Authorize implementation after incorporating these changes, especially: no raw request text in review exports; shared execution-plan generation; stable review IDs and append-only labels; actor versus channel separation; event schema bump; strict separation of synthetic and organic review queues.

v2.4.5 should produce the first artifact genuinely usable for independent human labeling rather than merely operational inspection.
